## 1. Character animation (companion, 4–5 reaction states)

**Options compared:** Rive + `@rive-app/react-canvas`, Lottie (`lottie-react`/`@lottiefiles/dotlottie-react`), CSS/SVG sprite swaps, emoji/GIF.

### Rive
- Rive ships a React integration built on the `useRive` / `useStateMachineInput` hooks; a state machine's inputs are `Trigger` (fire a one-shot transition), `Number`, and `Boolean` — which map almost exactly onto "idle / thinking / offended / tempted / celebrating" as five states driven by one enum-like input from your backend event type. [Rive React docs](https://rive.app/docs/runtimes/react/react), [State Machines guide](https://help.rive.app/runtimes/state-machines)
- `onStateChange` gives you a callback with the current state name(s), useful for the companion knowing when an animation has finished so it can, e.g., re-enable input. [Rive React docs](https://rive.app/docs/runtimes/react/react)
- **Free community character assets:** browsing `rive.app/community` turned up "Rive App Mascot — Cloud Character with State Machine & 6 Expressions" by AnggaMotion — a production-ready mascot with a built-in state machine and 6 expression states (idle/happy/sad/etc. — more than the 4–5 you need), which is about as close to a drop-in fit as this research found. It's licensed **CC BY 4.0** (commercial use + modification allowed, attribution required). [Asset page](https://rive.app/community/files/26964-50676-rive-app-mascot-cloud-character-with-state-machine-and-6-expressions/) — confirmed by direct fetch of the page.
- Rive's official community license: "Community files are all shared under a CC BY license" — so any other free character you pull from `rive.app/community` (shopkeeper/robot/blob included) should carry the same commercial-use-with-attribution term, but **verify per-file** since creators occasionally post under other terms — the community overview doc is the place to check per-asset. [Community Overview](https://help.rive.app/community/overview)
- Rive's own runtimes (the code that plays `.riv` files, including `@rive-app/react-canvas`) are MIT-licensed open source, independent of the file license. [GitHub rive-runtime LICENSE](https://github.com/rive-app/rive-runtime/blob/main/LICENSE)
- **Cost gotcha:** the Rive *editor* free tier lets you design/preview for free, but exporting a `.riv` file for shipping into an app requires a paid plan (Cadet $9/mo is the new cheapest tier). This matters only if you plan to *edit* a community file yourself (e.g. re-skin the mascot or add a state); if you use a community `.riv` as-is and only write code against it, you don't need to open the paid editor at all. [SpotSaas Rive pricing breakdown](https://www.spotsaas.com/product/rive/pricing) — **UNVERIFIED against Rive's own pricing page directly**, cross-check `rive.app/pricing` before committing budget.

### Lottie / dotLottie
- LottieFiles' public animation library is under the **Lottie Simple License**: free download/reproduce/modify/publish/distribute/publicly-display for commercial use, no attribution required. [Lottie Simple License](https://lottiefiles.com/page/license)
- `dotLottie` (the newer `.lottie` container format + `@lottiefiles/dotlottie-react` player) and its spec/SDKs are MIT-licensed open source. [dotLottie spec](https://dotlottie.io/), [`@lottiefiles/dotlottie-react` on npm](https://www.npmjs.com/package/@lottiefiles/dotlottie-react)
- LottieFiles has a large "free animations for React" category to browse for mascot/shopkeeper/robot-style loops. [LottieFiles free React animations](https://lottiefiles.com/free-animations/react)
- Lottie animations are **timeline-based loops**, not true state machines — driving 5 distinct reaction states means either (a) 5 separate small `.json`/`.lottie` files swapped by React state, or (b) one file with named segments played via `playSegments`. Both are simpler mentally than Rive's state-machine graph but give you less built-in blending between states.

### CSS/SVG sprite swap or emoji/GIF
- Fastest possible path for someone who is not an animator: 5 static PNG/SVG poses (or even 5 emoji/short GIFs) swapped via a CSS class or conditional render keyed off the backend event type. Zero animation tooling, zero license research, and it reads clearly on a screen from the back of a room — arguably *better* for demo legibility than a subtle Rive blend that judges won't notice from a distance.
- Trade-off: it looks "hackathon-y" rather than "polished," which matters if the pitch leans on production quality (Shopify design criterion).

### Recommendation
Use a **free CC BY Rive community mascot with a pre-built state machine** (e.g. the AnggaMotion cloud mascot, or search `rive.app/community` day-of for a shopkeeper/robot/blob variant with ≥4 expression states) driven via `@rive-app/react-canvas`'s `useStateMachineInput`, mapping your backend's `CompanionState` enum straight onto a `Number` or string input. This gets you polished, spontaneous-looking reactions without touching the Rive editor, for the cost of ~30–60 minutes hunting the community gallery for the right character and wiring 5 input values. **Time estimate: 2–3 hours** (asset search + wiring + testing all 5 transitions), assuming you find a state machine that already has ≥4 of your 5 states — if you have to *edit* the state machine yourself in the Rive editor, add 2+ hours and a possible $9/mo Cadet-plan purchase to export changes. Fallback if no suitable free asset is found in the first 45 minutes of searching: drop to the CSS/emoji sprite-swap path — it is a same-day, zero-license-risk path that still hits all 5 states, just less "alive."

## 2. Chat UI (companion panel)

**Options compared:** build from scratch, Vercel AI SDK UI `useChat`, assistant-ui, chatscope, shadcn chat blocks.

- **Vercel AI SDK `useChat`:** AI SDK now standardizes on **Server-Sent Events (SSE)** as its streaming transport — "natively supported in all major browsers," with built-in keep-alive/ping and reconnect. The hook wires `POST /api/chat` → `streamText` → SSE chunks → UI automatically, and supports custom message types / typed "data parts" for streaming arbitrary structured payloads (useful for streaming your `NegotiationEvent`/companion-state alongside text). [AI SDK UI stream protocol docs](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol), [AI SDK 5 announcement](https://vercel.com/blog/ai-sdk-5)
- **assistant-ui:** free/open-source, builds on shadcn so components live in your repo (you own the code), and includes a "runtime layer" — thread management, streaming, tool-call rendering, generative UI — out of the box; integrates with the Vercel AI SDK and LangChain. Heavier than a plain component kit but saves you writing streaming/message-state plumbing yourself. [designrevision comparison](https://designrevision.com/alternatives/assistant-ui), [ai-tldr.dev overview](https://ai-tldr.dev/learn/building-ai-apps/ai-ux-patterns/assistant-ui-chat-components/)
- **shadcn chat blocks:** copy-paste component templates (message bubbles, typing indicator, model selector) with minimal dependencies (shadcn/ui + Tailwind + Framer Motion) — you own all the state logic yourself. Good if you want full control and don't need thread/tool-call plumbing. [shadcn.io chat block](https://www.shadcn.io/blocks/chat-ai-assistant), [shadcn/ui chat components changelog (2026-06)](https://ui.shadcn.com/docs/changelog/2026-06-chat-components)
- **chatscope:** a standalone React chat-UI component library (not evaluated in depth here — no primary-source page was fetched; treat any specific claim about it as **UNVERIFIED**). It predates the AI-SDK ecosystem and isn't built around streaming-token UX the way the above three are.
- **SSE vs WebSocket for a Hono backend:** Hono ships `streamSSE` in `hono/streaming`, handling SSE framing, ping/keep-alive, and abort-signal wiring for you — this is less code than standing up `hono/*`'s `upgradeWebSocket` (which additionally requires a runtime-specific adapter: Cloudflare Workers, Deno, Bun, or `@hono/node-server`'s v2 WS support). [Hono Streaming Helper docs](https://hono.dev/docs/helpers/streaming), [Hono WebSocket Helper docs](https://hono.dev/docs/helpers/websocket). Since chat is inherently "user sends a message via a normal POST, then reads a stream of tokens back" — one-directional server→client push per turn — SSE is a strictly sufficient transport and doesn't need a persistent bidirectional socket.

### Recommendation
**Vercel AI SDK `useChat` over SSE, styled with shadcn/ui primitives (optionally assistant-ui's message-list/thread components if you want less boilerplate).** This is the path with the most current documentation, native Hono-compatible SSE, and the least custom state-management code to write under time pressure. Skip assistant-ui's full runtime unless you specifically need multi-thread history — for a single companion-panel conversation per session it's more infrastructure than the demo needs. **Time estimate: 2–3 hours** to get a working streaming chat panel with product cards and a "Deal — checkout" button rendered as a custom message/tool-call UI part.

## 3. Charts (Merchant Console histogram, 300 points, slider-driven re-render)

**Options compared:** Recharts, visx, Observable Plot, plain SVG/D3.

- **Recharts:** re-renders the entire chart tree on every prop change. Clean React mental model, simplest API, but potentially "jarring if data updates are frequent." It remains "the practical default for many React dashboards" because of API simplicity. [LogRocket 2026 React chart libraries](https://blog.logrocket.com/best-react-chart-libraries-2026/), [devpick Recharts vs visx](https://devpick.co/recharts-vs-visx-visx)
- **visx (Airbnb):** low-level D3-in-React primitives — you compose the SVG yourself, giving full control over what re-renders and when (e.g. you can re-render only the bars/reference-lines, not axes/legend, on every slider tick). Still SVG-based, not canvas, so raw draw cost is comparable to Recharts for the same element count; the win is *avoiding unnecessary re-renders of unrelated chart parts*, not GPU acceleration. Actively maintained as of Sept 2026 (issues opened as recently as Sept 1, 2026) though community members have noted a slower release cadence. [airbnb/visx GitHub](https://github.com/airbnb/visx), [maintenance discussion #1908](https://github.com/airbnb/visx/discussions/1908)
- **Observable Plot:** extremely concise API (a histogram that's ~50 lines of raw D3 can be ~1 line of Plot), and Plot's histogram binning (Scott's rule, capped at 200 bins) is a better default than D3's for this data size. But Plot "doesn't give you many ways of customizing or adding interactivity" and is positioned for exploration/notebooks, not for a chart you need to re-render at slider-drag frame rates with custom vertical reference lines layered on top and driven by external React state. [vis4.net Plot review](https://www.vis4.net/blog/2023/09/observable-plot-review/), [Medium: Plot a stepping stone to D3](https://medium.com/@Naraina_Damle/observable-plot-a-stepping-stone-to-d3-35cad5f64e51)
- **Plain SVG/D3:** maximum control and maximum time cost — you'd hand-roll binning, scales, and reference-line overlays. For 300 points redrawn at 60fps on drag this is very doable (300 SVG rects is trivial for a browser), but it's the highest line-count option, which is the wrong trade for a 24–32 h solo front-end build.
- **High-frequency-update note:** for genuinely high-frequency (many-times-per-second) updates, Canvas-based charting (Chart.js, ECharts) has an edge because it bypasses React's reconciler — but a slider-drag histogram redraw is bounded by drag events (tens of times per second, not hundreds), well within what SVG + Recharts/visx handles smoothly. [LogRocket 2026 comparison](https://blog.logrocket.com/best-react-chart-libraries-2026/)

### Recommendation
**Recharts**, with the histogram bars + three vertical `ReferenceLine`s (list, floor, blanket-sale) computed client-side from the 300-point `GymResult` array on every slider `onChange`. It's the lowest-code path to "overlaid histogram with reference lines that updates as a slider drags," and at 300 data points/bars the "re-renders the whole tree" cost is not perceptible — this is well within Recharts' comfort zone; only reach for visx if profiling in rehearsal shows visible jank (unlikely at this data size). Debounce the slider's re-render to `requestAnimationFrame` if you see stutter rather than switching libraries. **Time estimate: 2–3 hours** for the chart + reference lines + wiring to slider state; +1 hour if you add the second overlaid histogram (Policy A vs Policy B) from §8.3 of the spec.

## 4. Storefront look

**Options compared:** Tailwind + shadcn/ui from scratch, a free e-commerce template, embedding inside a real Shopify dev-store theme (script tag/app embed). Plus a dedicated look at Polaris for the Merchant Console.

### Fastest storefront path
- **Tailwind + shadcn/ui, freehand:** full control, but you're writing a product page, cart affordance, and layout from zero.
- **Free shadcn/ui e-commerce templates exist and can be forked directly** — e.g. "Relivator," an open-source Next.js 15/React 19 + shadcn/ui + Tailwind e-commerce template, plus several template galleries (shadcnblocks, shadcnuikit, shadcntemplates) with dedicated e-commerce categories including product-listing/cart/checkout layouts. [shadcntemplates e-commerce category](https://shadcntemplates.com/category/ecommerce), [AdminLTE.IO shadcn templates roundup](https://adminlte.io/blog/shadcn-ui-templates/) — **treat specific template names/licenses as leads to verify, not settled facts**; check each template's own license file before using it, since "free" template galleries mix MIT, personal-use-only, and paid tiers.
- **Real Shopify dev-store theme embed:** Shopify's current (and only forward-compatible) mechanism for injecting your own script/UI into a theme without editing `theme.liquid` directly is a **theme app extension with an app embed block** — merchants (you) activate it in Theme Editor → Theme Settings → App embeds, and Shopify injects it before `</head>` or `</body>` per your block's `target` config. Directly editing `theme.liquid` / using the legacy Script Tag API to inject assets is explicitly called out as the **legacy** approach that theme app extensions replace. [Shopify docs: App blocks for themes](https://shopify.dev/docs/storefronts/themes/architecture/blocks/app-blocks), [Shopify docs: Migrate to theme app extensions](https://shopify.dev/apps/online-store/theme-app-extensions/update)

### Recommendation (storefront)
For a hackathon demo where the "store" itself is fake/staged and the real payoff is the negotiated checkout, **build the product page yourself in Tailwind + shadcn/ui** (optionally forking a free shadcn e-commerce template as a starting skeleton to save layout time) rather than embedding in a real Shopify theme. The Shopify theme-embed path is real and well-documented, but it adds theme-editor setup, app-extension scaffolding, and a second surface (real Shopify storefront rendering) to get right under time pressure — and per the team plan, the *real* Shopify surface that must work flawlessly is the checkout tab at settlement, not the browsing page. Reserve theme-embed effort only if you have slack time after the H24 gate and want the "looks native to a real store" flex for judges. **Time estimate: 2 hours** for a clean fake storefront (hero product image, price, size selector, add-to-cart) using shadcn primitives, forking a template if one fits your product photos.

### Shopify Polaris for the Merchant Console — current state (2026)
- **Polaris React is deprecated.** Its own repo README states verbatim: *"The Shopify Polaris React library is deprecated. We are no longer accepting contributions or feature requests in this repository."* On **October 1, 2025** Shopify released **Polaris Web Components** as the successor, and directs developers to `shopify.dev/docs/api/polaris` for current usage. [Shopify/polaris-react GitHub README (fetched directly)](https://github.com/Shopify/polaris-react)
- Official current docs confirm: Polaris Web Components are framework-independent (built on the Web Components standard, not React), are what Shopify CLI now scaffolds by default for new apps (loaded via a `polaris-1.js` script tag that tracks the newest stable v1 release), and Shopify explicitly "encourages Shopify App developers to adopt Polaris Web Components for new development." [Shopify docs: Using Polaris web components](https://shopify.dev/docs/api/polaris/using-polaris-web-components), [Shopify docs: Polaris references](https://shopify.dev/docs/api/polaris)
- Practical friction reported by developers migrating: Polaris Web Components are missing some features present in Polaris React, and community forum threads note frustration with gaps as of the transition. [Shopify community forum thread](https://community.shopify.dev/t/is-anyone-else-disappointed-with-polaris-web-components-so-many-missing-features/23687) — this is a forum post, not an official statement, so treat the *severity* of the gap as **UNVERIFIED**, but the existence of a transition-period feature gap is corroborated by multiple independent write-ups. [No7 Software: Polaris Web Components Migration](https://no7software.co.uk/blog/polaris-web-components-migration-embedded-apps)
- Polaris Web Components are also framework-agnostic — they don't require React at all, meaning wiring them into a Vite + React app means using them as custom elements rather than idiomatic React components (no first-class React props/typing layer the way Polaris React had one).

### Recommendation (Polaris)
**Do not adopt Polaris (React or Web Components) for the Merchant Console.** Polaris React is officially deprecated and shouldn't be started fresh; Polaris Web Components are the "right" long-term answer but are framework-agnostic custom elements with a reported feature gap mid-migration — both add integration friction (wrapping custom elements in React, or, if you go React anyway, going against Shopify's own current recommendation) for a purely cosmetic payoff on a screen your buyer-facing judges won't even see. The Merchant Console's actual differentiators — live event feed, sliders wired to a re-rendering histogram, and a red PAUSE button — are generic UI you build faster and more reliably in Tailwind + shadcn/ui, which also matches the spec's own repo layout note (`merchant-console` app "Vite + React + Polaris-style," i.e., visually Polaris-*inspired*, not literally the Polaris library). **Time cost avoided: likely 3–5 hours** of Web Components integration friction for a "looks native to Shopify admin" effect that's not worth it at this data point — Tailwind can approximate the Polaris visual language (spacing, muted grays, card borders) in under an hour with no library risk.

## 5. Voice (stretch)

**Options compared:** OpenAI Realtime API vs (browser Web Speech API STT + ElevenLabs TTS) vs OpenAI `gpt-4o-mini-tts` / `gpt-4o-transcribe` endpoints. **Constraint that decides the winner:** code, not the LLM, must decide the actual reply content and price — the voice/LLM layer must never be free to converse about price.

- **OpenAI Realtime API (`gpt-realtime`):** achieves ~800ms voice-to-voice latency when configured well, and its function-calling reliability improved to 66.5% on ComplexFuncBench Audio (up from 49.7% on the prior model) — meaning it *can* call a tool mid-conversation and resume speaking from the tool's result, but a two-in-three-ish reliability figure on complex function calls is a real risk if you let the *model* decide when/how to invoke your price tool rather than constraining the conversation flow in code. Pricing: audio input ~$32/M tokens (~$0.06/min), audio output ~$64/M tokens (~$0.24/min); cached input is ~80× cheaper. [Forasoft OpenAI Realtime API production guide](https://www.forasoft.com/blog/article/openai-realtime-api-voice-agent-production-guide-2026), [TokenMix cost/latency writeup](https://tokenmix.ai/blog/openai-realtime-voice-api-2026-cost-latency) — pricing figures should be cross-checked against `openai.com/api/pricing` before the demo since third-party aggregator pages can lag.
- **Browser Web Speech API (STT) + ElevenLabs (TTS):**
  - STT support: Chrome and Edge have full `SpeechRecognition` support (Chrome 139+ even added on-device/offline recognition); Safari supports it from macOS 14.1+/iOS 14.5+ via the `webkitSpeechRecognition` prefix (with a standard `window.SpeechRecognition || window.webkitSpeechRecognition` fallback); Firefox has it behind a disabled-by-default flag. [MDN SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition), [testmuai browser-support summary](https://www.testmuai.com/learning-hub/speech-recognition-api-browser-support/) — demo on Chrome/Edge to avoid Firefox entirely.
  - ElevenLabs free tier: **10,000 credits/month**, ~10 min of Multilingual v2 TTS or ~15 min of Conversational AI agent time (Flash models are 0.5 credits/char, i.e. roughly double the minutes); **~10 concurrent requests**; **no commercial license on the free plan** — the cheapest paid tier with a commercial license is Starter at $6/mo. [ElevenLabs pricing page (fetched directly)](https://elevenlabs.io/pricing)
  - **MLH partner offer:** ElevenLabs is a confirmed MLH partner; hackathon participants registered for an MLH event receive an email with a promo code for a **free 3-month ElevenLabs subscription**, plus demo app/docs/tutorial resources. [MLH ElevenLabs partner page (fetched directly)](https://www.mlh.com/partners/elevenlabs) — whether Hack the North specifically is MLH-affiliated and whether this promo is live for it is **UNVERIFIED**; confirm with event organizers or the MLH events/prizes page before counting on it. A separate MLH prizes page mentions winners at some MLH events receiving ElevenLabs-branded wireless earbuds as a sponsor prize, which is a different, event-specific thing from the subscription promo code. [MLH prizes page](https://www.mlh.com/events/prizes)
  - Because this pipeline is STT → text → **your code decides the reply text and price** → TTS speaks exactly that text, this path gives you full, code-level control over what gets said. The LLM (if used at all) only ever sees the job of *phrasing* — never deciding numbers — matching the spec's own "never trust an LLM with a floor" rule (§5.2 of `../archive/v2-spec.md`).
- **OpenAI `gpt-4o-mini-tts` / `gpt-4o-transcribe` / `gpt-4o-mini-transcribe`:** per-token or per-minute billed. `gpt-4o-transcribe` ≈ $2.50/$10 per M input/output tokens or $0.006/min; `gpt-4o-mini-transcribe` ≈ $1.25/$5 per M or $0.003/min; `gpt-4o-mini-tts` ≈ $0.60/M text-input tokens + $12/M audio-output tokens (~$0.015/min of audio). [OpenAI model docs via aggregator pricing pages](https://openrouter.ai/openai/gpt-4o-transcribe), [gate.ai gpt-4o-mini-transcribe pricing summary](https://gate.ai/blog/gpt-4o-mini-transcribe-openai-specs-pricing-api-use-cases) — cross-check against `platform.openai.com/docs/pricing` directly since these are third-party summaries. Like the browser+ElevenLabs path, these are discrete STT/TTS calls you call explicitly around your own code's decision — not a live bidirectional session — so they preserve the same "code decides, model only phrases" control.

### Which pipeline best preserves "code decides the price"?
The **discrete pipeline** (STT → your code → TTS), whether that's browser STT + ElevenLabs TTS or OpenAI's transcribe/TTS endpoints, structurally cannot let the model free-associate about price: the LLM (if invoked at all, e.g. via the existing Strategist call) only ever produces the *public_reasoning* string that gets spoken, exactly as the text-chat path already works per the spec (§7.4). **OpenAI Realtime API is architecturally the wrong fit for this constraint** — it's designed for the model to drive the whole spoken turn including deciding when to call tools, which is precisely the "let the LLM freely converse" failure mode the spec explicitly guards against ("Never trust an LLM with a floor," §5.2). Using Realtime would require you to fight the API's own design (hard-constrain every response via function-call-only outputs) for no latency win big enough to justify it in a demo context.

### Recommendation
**Browser Web Speech API for STT + ElevenLabs (or OpenAI TTS if ElevenLabs free-tier concurrency/quota is tight) for TTS**, both invoked explicitly around your existing Strategist call so the spoken reply is always the same `public_reasoning` string your text chat already renders — zero new "can the model say a number it shouldn't" surface area. Register for MLH's ElevenLabs promo code immediately (it's a day-0 checklist item, not a build task) to lift the free-tier's 10k-credit/10-concurrent ceiling if voice becomes a heavily-rehearsed demo beat. **Time estimate: 2–3 hours** for push-to-talk STT + TTS playback wired to the existing negotiation reply pipeline, assuming the reply-generation code path already exists from the text chat (per the team plan, voice is explicitly P3's post-H24 stretch, budgeted after the core Arena/Console work).

## 6. Realtime plumbing (backend → chat panel + Merchant Console)

- **Direction of traffic:** the dominant traffic pattern here is server→client fan-out of `NegotiationEvent`/Gym/companion-state updates to two simultaneously-open surfaces (chat panel, console) — not client→server streaming. Actions like "drag a slider," "hit PAUSE," or "send a counter-offer" are one-shot requests better served by a normal HTTP POST than by pushing them down the same channel.
- **SSE vs WebSocket for this shape:** SSE is a read-only, HTTP-native protocol that "can be load-balanced without worrying about two-way routing," and is explicitly well-suited to "broadcast-style communication, where the same data must be delivered to many clients simultaneously" — the exact shape of pushing one event stream to both the chat panel and the console at once. WebSocket earns its complexity when the client must also *push* data down the same channel continuously (e.g., true bidirectional voice audio), which for this app is isolated to the voice stretch goal, not the core event feed. [websocket.org SSE vs WebSocket comparison](https://websocket.org/comparisons/sse/), [germano.dev SSE writeup](https://germano.dev/sse-websockets/)
- **Simplest Hono setup:** `hono/streaming`'s `streamSSE` helper handles SSE framing, keep-alive pings, and abort-signal cleanup for you in a single route handler — you `writeSSE({ data, event, id })` per event and the client's native `EventSource` (or the AI SDK's SSE client) does automatic reconnect. [Hono Streaming Helper docs](https://hono.dev/docs/helpers/streaming). The WebSocket alternative (`hono/*`'s `upgradeWebSocket`) additionally requires picking a runtime-specific adapter (Cloudflare Workers/Deno/Bun, or `@hono/node-server`'s v2 WS support) before you can even open a route. [Hono WebSocket Helper docs](https://hono.dev/docs/helpers/websocket)
- **Fan-out mechanics:** with SSE, both the chat panel and console simply open their own `GET /events` connection to the same Hono process; your server keeps an in-memory list of open `SSEStreamingApi` handles (or a tiny pub/sub if you split into multiple processes per the team plan's `deal-agent ×3` / `buyer-agent` split) and calls `writeSSE` on all of them when a `NegotiationEvent` or `GymResult` fires. This is the same mechanism the team plan's "P1 → P3, one WebSocket channel" contract describes conceptually — the transport detail (SSE vs WS) doesn't change the shared-type contract, only how you open the pipe.
- **Shared typed event union:** put a `packages/protocol` (or a small dedicated `packages/events`) workspace package exporting a single discriminated union, e.g. `type BazaarEvent = { type: "offer_landed"; ... } | { type: "companion_state"; state: CompanionState } | { type: "gym_result"; ... } | ...`, and have both `apps/arena`/`apps/merchant-console` and the backend `apps/deal-agent`/`apps/buyer-agent` import it via a pnpm workspace path. This is the standard cross-package-type-sharing pattern in a TS monorepo (Turborepo/Nx/pnpm workspaces) — a shared package is the "cleanest solution" precisely because it eliminates drift between what the backend emits and what each front end expects to narrow on `event.type`. [DEV Community: sharing TS types across a monorepo](https://dev.to/aoda-zhang/making-a-typescript-shared-package-work-across-frontend-and-backend-in-a-monorepo-1k23), [Useful Functions: sharing types across TS monorepos](https://www.usefulfunctions.co.uk/2025/11/07/sharing-types-across-typescript-monorepos/). This also matches — and should literally *be* — the team plan's `NegotiationEvent`/`GymResult` contract files (§7 of `../archive/v2-team-plan.md`), just typed as a discriminated union instead of one flat shape, so the client can `switch (event.type)`.

### Recommendation
**Server-Sent Events via Hono's `streamSSE` helper for all backend→front-end pushes (companion state, offer cards, console feed, Gym results), plain HTTP POST for all client→server actions (counter-offer, pause, slider "adopt"), and a single shared discriminated-union `BazaarEvent` type in a workspace package imported by both front ends and both backend apps.** Reserve WebSocket only for the voice stretch goal's raw audio streaming, if you build push-to-talk beyond a simple "record → POST blob → get audio back" round trip. This is materially less server setup than WebSocket (no runtime-specific adapter, native browser reconnect) while fully covering the actual traffic shape the two screens need. **Time estimate: 1–2 hours** to stand up the SSE route + shared event-type package + a `useSSE`-style React hook consumed by both Arena/companion and Console.

## 7. Hosting for demo day

- **Localhost + Cloudflare Tunnel:** a tunnel makes an *outbound* connection from your laptop to Cloudflare, so you never need the venue network to allow inbound traffic, port-forwarding, or a static IP — sidestepping the actual common failure modes at hackathon venues (hotel-style/conference WiFi, NAT, router client-isolation, captive portals). [recca0120 2026 Cloudflare Tunnel writeup](https://recca0120.github.io/en/2026/04/14/cloudflare-tunnel-2026/), practical hackathon example: [GitHub issue: expose live dashboard via Cloudflare Tunnel](https://github.com/Trolleroof/handoff-comma-lemma-hackathon/issues/19)
  - WebSockets over Cloudflare Tunnel/Cloudflare's edge have worked by default since 2022 (no special flag needed on the Cloudflare side), though a config setting `ws: true` on some tunnel/ingress configs is still worth explicitly setting for older `cloudflared` config formats. [Cloudflare docs: WebSockets](https://developers.cloudflare.com/network/websockets/), [Cloudflare community: are websockets supported via tunnels](https://community.cloudflare.com/t/are-web-sockets-in-fact-supported-via-tunnels/539971)
  - Caveat: you're still dependent on *your own* laptop's WiFi/hotspot uplink to reach Cloudflare's edge in the first place — a tunnel removes inbound-networking risk, not "the venue WiFi is down entirely" risk. Bring a phone hotspot as backup uplink.
- **Deploying to Vercel:** Vercel Functions now claim native WebSocket support for realtime features, but with an important caveat — "established connections are pinned to the Function for its maximum duration, and future connections are not guaranteed to connect to the same Function," which is a real risk for a long-lived demo connection across a multi-minute pitch. Vercel's own KB explicitly lists SSE and external dedicated WebSocket servers/third-party pub-sub as the fallback/complementary patterns for cases where you need more reliable long-lived connections. [Vercel KB: do Serverless Functions support WebSocket](https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections), [community thread on fluid compute + websockets](https://community.vercel.com/t/does-vercel-support-websockets-now-that-we-have-fluid-compute/27205)
- **Railway / Fly.io:** both run your app as a genuine long-lived process rather than a request-scoped serverless function, so a WebSocket (or SSE) connection just stays open with no special handling. Railway specifically documents that WebSocket connections are exempt from its inactivity timeouts and can stay open indefinitely; Fly.io's own blog states that WebSocket servers "work correctly on Fly.io" with no serverless cold-start or connection-limit caveats. [Railway Socket.IO deploy guide](https://docs.railway.com/guides/socketio), [Fly.io blog: WebSockets and Fly](https://fly.io/blog/websockets-and-fly/)

### Which is safest given flaky venue WiFi?
For a **judge walking up to your laptop / a projector plugged into your machine**, the connection path is: judge's eyes → your screen. There is no "judges' own devices connecting over WiFi to your app" requirement unless you specifically want remote judges to load the app on their own phones — re-read the demo script in `../archive/v2-spec.md` §14: the whole demo (Arena, Console, checkout tab, judge speaking into *your* mic) runs on your own machine/screen. That collapses the real risk down to "does *my* laptop's connection to the internet (for Shopify Admin API calls, Backboard, OpenAI/ElevenLabs) survive," not "can external judges reach my server." Given that:
- **Cloudflare Tunnel from your own laptop** is the standard hackathon answer specifically because it removes inbound-networking failure modes and needs no deploy step — you're already running the app locally for development, so demo day requires zero additional deploy risk, just `cloudflared tunnel run` pointed at your local Hono server. This also means your Shopify Admin token / API keys never leave your machine's environment.
- If you want a fixed, pre-provisioned public URL that survives your laptop reconnecting (e.g., WiFi drops mid-demo and you need to switch to a hotspot without changing the URL judges/backup recording depend on), **Railway or Fly.io deployment** is the safer choice precisely because the process — and therefore the WebSocket/SSE connections — don't depend on your physical laptop's network at all; you'd need to `git push`/`fly deploy` ahead of time and rehearse against the deployed URL, not localhost.
- **Vercel is the weakest fit** here specifically because of the "reconnect may hit a different Function instance" caveat for anything long-lived — avoid it for the SSE/WebSocket event surface even if you use it for a purely static piece (e.g., the `.well-known`/directory JSON files the spec already plans to host there, which are stateless and unaffected by this caveat).

### Recommendation
**Primary: Cloudflare Tunnel from the presenting laptop**, since the whole demo is designed (per the spec's own demo script) to run on one machine anyway, and a tunnel eliminates the actual failure modes venue WiFi introduces (inbound NAT/firewall, captive portals) with a single `cloudflared` command and zero deploy pipeline to maintain. **Fallback: deploy the same Hono app to Railway** (simplest long-running-process PaaS with documented indefinite WebSocket/SSE support) as a pre-tested backup URL, and rehearse switching to it once, so that if the presenting laptop's uplink dies entirely mid-pitch you have a second, network-independent path plus the spec's own `DEMO_OFFLINE=1` replay mode as the true last resort. **Time estimate: 1 hour** to set up and test the Cloudflare Tunnel + stable subdomain, **+1 hour** for a one-time Railway deploy as backup, done well before H24 gate — not on Sunday morning.
