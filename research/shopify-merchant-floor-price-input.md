# Shopify — Merchant Floor-Price Input: Where Should It Live?

**Audience:** the team deciding where the merchant sets "the lowest price / minimum margin my AI shopkeeper may go to" — per store, and possibly per product — for a 32h hackathon build (TypeScript, Hono backend, one dev store, existing custom-app Admin API token scoped `read_products`, `read_inventory`, `write_discounts`).
**Scope:** four build options only — own Console page, metafield no-code, Admin UI extension, embedded app (App Bridge). Not product/negotiation logic.
**Method:** WebSearch to find candidate pages, WebFetch to confirm the actual claim against the primary source page (shopify.dev / help.shopify.com only). Anything not confirmable against a fetched primary-source page is marked **UNVERIFIED** with a reason.
**Research date:** 2026-09-19. Shopify's admin-extension tooling (React → Preact/Remote DOM) and the custom-apps-in-admin flow both changed materially around January 2026 — re-check live docs before relying on any deadline/version number here.

**Bottom line (judgement, not sourced):** for per-store, the Console page is by far the cheapest and lowest-risk; for per-product, the metafield no-code path is nearly as cheap and gets a genuinely native Shopify UI for free. Neither UI-extension nor full embedded-app work is justified by this one input field alone within 32 hours.

### 1. Metafields with no extension code

- **Where definitions are created:** Settings → **Metafields and metaobjects** (also called "Custom data") in Shopify admin, at `admin.shopify.com/settings/custom_data`, lets a merchant (or the team, using the same admin login) create a metafield definition for a given resource type without writing code. [Overview of custom data](https://help.shopify.com/en/manual/custom-data/overview), [Creating custom metafield definitions](https://help.shopify.com/en/manual/custom-data/metafields/metafield-definitions/creating-custom-metafield-definitions) — the latter states definitions can be created "alternatively... from Settings > Metafields and metaobjects."
- **Resource types this section covers:** products, variants, customers, orders, collections, transfers, locations, company, company location. **"Shop" is not listed as a resource type** in the custom-data options page. [Options for custom data](https://help.shopify.com/en/manual/custom-data/options)
- **Editing the value once defined:** happens on the resource's own admin detail page (e.g. a specific product page, under a "Metafields" section), per [Adding values to metafields](https://help.shopify.com/en/manual/custom-data/metafields/adding-values-to-metafields), which walks through product/collection/customer detail pages only — **no shop-level page is described**.
- **Reading via Admin GraphQL:** the standard shape is `product { metafield(namespace: "bazaar", key: "floor_price") { value } }` against the `Metafield` object. [Metafield object reference](https://shopify.dev/docs/api/admin-graphql/latest/objects/Metafield)
- **Scopes needed:** shopify.dev's access-scopes reference does **not** list a dedicated "metafield" OAuth scope for product/shop metafields (only metaobjects get their own `read_metaobjects`/`write_metaobjects` scopes). [Shopify API access scopes](https://shopify.dev/docs/api/usage/access-scopes) — **UNVERIFIED**: this page never explicitly states "`read_products` is sufficient to read a product's metafields"; that specific sentence wasn't found on a primary-source page, though metafields are queried as a sub-field of `product` and no separate scope is documented, so it is the reasonable reading.
- **App-owned vs. merchant-owned access, for a *third-party* app reading someone else's definition:** this is a separate access-control layer from OAuth scopes. Merchant-owned definitions (any namespace other than the reserved `$app` one) are, per Shopify's own wording, **"Always full access — readable and writable by merchants and all apps with appropriate scopes."** App-owned (`$app` namespace) definitions are controlled by the creating app; another app only gets admin/UI access if `access.admin` is set to `merchant_read_write`. [Access controls for metafields](https://shopify.dev/docs/apps/build/custom-data/metafields/definitions/use-access-controls-metafields), [Manage metafield definitions](https://shopify.dev/docs/apps/build/metafields/definitions). Since the team would create `bazaar.floor_price` themselves (as a normal, non-`$app`-namespaced definition), this is not a blocker for them.
- **`metafieldDefinitionCreate` + pinning:** the mutation exists and is the documented way to create a definition programmatically. [`metafieldDefinitionCreate`](https://shopify.dev/docs/api/admin-graphql/latest/mutations/metafieldDefinitionCreate) — **correction to the stated hypothesis:** its input type has no `pin` boolean field. Pinning (making the field show prominently in admin) is a **separate** mutation, `metafieldDefinitionPin`, called after creation. [`metafieldDefinitionPin`](https://shopify.dev/docs/api/admin-graphql/latest/mutations/metafieldDefinitionPin)
- **Dev-store gotchas:** definition-count limits are per-plan (128 definitions per resource type on Basic/Shopify/Advanced, 256 on Plus/Enterprise) — irrelevant at the scale of one `floor_price` definition. [Metafield limits](https://shopify.dev/docs/apps/build/metafields/metafield-limits) — whether a development store specifically inherits one plan tier or another for this limit is **UNVERIFIED** (not stated on this page), but immaterial here.
- **Shop-level metafield — the key unresolved fact, now resolved:** Shop **is** a valid `MetafieldOwnerType`, and a 2026 changelog entry states shop metafield **definitions and values** are "now... exposed in the Shopify Admin UI." [Shop metafield definitions now in Admin changelog](https://shopify.dev/changelog/shop-metafield-now-in-admin) — but this entry is ambiguously worded and never names a specific Settings screen. Cross-checking it against the two help-center pages that actually walk through the "add a value" flow ([Adding values to metafields](https://help.shopify.com/en/manual/custom-data/metafields/adding-values-to-metafields)) and the resource-type list ([Options for custom data](https://help.shopify.com/en/manual/custom-data/options)) — **neither mentions Shop as an editable resource** in Settings → Custom data. **Your hypothesis is confirmed as far as primary sources go**: there is no documented no-code admin UI to edit a *shop-level* metafield's value; the Custom Data section manages product/variant/order/customer/collection/company-type resources only. Shop metafield *definitions* being newer to the Admin API doesn't mean their *values* get a Settings-page editor — that specific claim could not be found stated anywhere, positively or negatively, on a primary-source page, so treat "no UI exists" as strongly-supported-but-not-100%-explicitly-stated (mark residual uncertainty **UNVERIFIED**).

### Recommendation
Per-**product** floor prices: use the no-code metafield path — 15–30 minutes of admin clicking, zero extension code, native UI, and a plain GraphQL read the team already has the scope for. Per-**store** floor price: since no no-code UI reaches a shop metafield's value, either (a) still use a shop metafield but set/update its *value* only via `metafieldsSet` from the team's own backend (which the Console page can trigger), or — simpler — (b) just put the store-wide floor in the team's own Console/DB and skip Shopify metafields for that case entirely. **Judgement: (b) is faster and removes the one uncertain fact from the critical path.**

### 2. Admin UI extensions (admin blocks on the product details page)

- **Target:** `admin.product-details.block.render` renders a block on the product detail page. [Block Extension API](https://shopify.dev/docs/api/admin-extensions/2025-07/api/target-apis/block-extension-api), [Build an admin block UI extension](https://shopify.dev/docs/apps/build/admin/actions-blocks/build-admin-block)
- **Tooling/framework, current and recommended:** the current (fetched) tutorial builds the extension in **Preact** (`preact`, `preact/hooks`) plus Shopify's own web components (`s-admin-block`, `s-table`, `s-select`, etc.), rendered via **Remote DOM**, not `@shopify/ui-extensions-react`. [Build an admin block UI extension](https://shopify.dev/docs/apps/build/admin/actions-blocks/build-admin-block) — React support for these extensions is deprecated as of API version 2025-07 per Shopify's own versioning cadence, though the exact final-retirement date is only corroborated by secondary aggregators, not a fetched shopify.dev changelog entry, so mark the precise **deadline** date **UNVERIFIED** while the "Preact/Remote DOM is current, React is legacy" direction is confirmed by the primary tutorial itself.
- **Setup:** Shopify CLI (3.78+ referenced for a `write_products`-scoped example), an app scaffolded with the extension, and `shopify app dev` to install a dev version onto the store. [Build an admin block UI extension](https://shopify.dev/docs/apps/build/admin/actions-blocks/build-admin-block)
- **Runs on a dev store without review:** confirmed — the tutorial's own requirements/testing flow is to preview directly on a development store; no app-review or listing step is described. [Build an admin block UI extension](https://shopify.dev/docs/apps/build/admin/actions-blocks/build-admin-block)
- **Direct API access from inside the extension:** confirmed — the docs state "you don't need proxy calls to the GraphQL Admin API through your app's backend," and show calling `fetch("shopify:admin/api/graphql.json", {...})` directly from the extension to read/write data (including metafields) with no backend round trip. [Build an admin block UI extension](https://shopify.dev/docs/apps/build/admin/actions-blocks/build-admin-block)

### Recommendation
**Time estimate (judgement, not sourced):** 4–8 hours for a developer who has never built a Shopify app before to get one working number input that reads/writes a metafield via direct `admin.graphql` calls, on a dev store — most of that time is learning Shopify CLI + the Preact/Remote DOM extension model and the dev-store install loop, not the input field itself. Worth it only if the team specifically wants the "feels 100% native to Shopify admin" polish and has slack after the core negotiation build; otherwise the no-code metafield path (§1) gets 90% of the same merchant-facing outcome for a fraction of the time.

### 3. Embedded app (App Bridge + Polaris)

- **Auth model:** current embedded apps use **token exchange**, not the classic OAuth redirect dance — App Bridge (loaded via a CDN script tag) mints a short-lived ID token (`shopify.idToken()`), the backend exchanges it at Shopify's token endpoint for an offline or online access token. [Set up embedded app authorization](https://shopify.dev/docs/apps/build/authentication-authorization/set-embedded-app-authorization?extension=javascript) — this same source calls out three prerequisites: app credentials from the Dev Dashboard, configured access scopes, and installation on a dev store.
- **"Managed installation":** Shopify CLI-scaffolded apps have Shopify manage the install/auth flow so the app doesn't hand-roll it. [About app authentication](https://shopify.dev/docs/apps/build/authentication-authorization) / related session-token docs.
- **App proxy — confirmed not needed:** an app proxy exists specifically to route **storefront**-facing URLs (e.g. `https://<shop>/apps/my-path`) to an external backend for customer-facing content; it is unrelated to and not required for an embedded **admin** page. [About app proxies and dynamic data](https://shopify.dev/docs/apps/build/online-store/app-proxies) — direct quote: "App proxies take requests to Shopify URLs, and proxy them to your app. This allows you to fetch and display data on a storefront from an external source."
- **Polaris React status — deprecated:** the `Shopify/polaris-react` GitHub repository's own README states verbatim, *"The Shopify Polaris React library is deprecated. We are no longer accepting contributions or feature requests in this repository,"* with **Polaris Web Components** as the named successor since October 1, 2025. [Shopify/polaris-react README](https://github.com/Shopify/polaris-react) — confirmed in the sibling frontend-tech research file and independently consistent with shopify.dev's own current docs directing developers to Polaris Web Components. [Using Polaris web components](https://shopify.dev/docs/api/polaris/using-polaris-web-components)

### Recommendation
**Time estimate (judgement):** 6–10+ hours for a first-timer to get a settings page with a number/slider input embedded in Shopify admin, POSTing to their own Hono backend — token-exchange auth, App Bridge wiring, and picking a UI approach (Polaris React is deprecated; Polaris Web Components are the "correct" but framework-agnostic, custom-element answer) all add friction beyond what a single settings field justifies. This is the most expensive and highest-risk of the four options for this specific feature; only worth it if the team plans a broader embedded-app surface beyond just this one input.

### 4. Legacy "custom app created in the store admin" (the team's existing token)

- **Still exists, but frozen for new apps:** Shopify's own help page states **"You can no longer create new admin-created custom apps. Existing apps are unaffected and continue to work,"** and separately references **"legacy custom apps created before January 1, 2026"** as the ones still manageable from Shopify admin. [About apps / custom apps](https://help.shopify.com/en/manual/apps/app-types/custom-apps), [Generate access tokens for admin-created custom apps](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/generate-app-access-tokens-admin) — the latter is the page that states the "no longer create new" line directly. New apps must go through the **Dev Dashboard** or **Shopify CLI** instead. [Create apps using the Dev Dashboard](https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard)
- **Can a custom-app-in-admin app have UI extensions or an embedded page?** Not stated explicitly on either fetched page — neither addresses extensions/embedded pages for this app type one way or the other, so that combination is **UNVERIFIED** by direct statement. What *is* clear from the tooling docs is that UI extensions and embedded-app scaffolding are built and shipped through the **Shopify CLI / Dev Dashboard** workflow (`shopify app init`, `shopify app dev`, extension targets, `shopify.app.toml`), which is a structurally different artifact from an admin-created custom app's simple "generate a token" flow. [Scaffold an app](https://shopify.dev/docs/apps/build/scaffold-app), [About Shopify CLI for apps](https://shopify.dev/docs/apps/build/cli-for-apps)
- **Can the team's existing token be upgraded/reused, or do they need a separate app?** Since the team's app was almost certainly created before this changeover (an admin-created custom app, generating a token directly via Settings → Apps and sales channels → Develop apps), **it cannot be extended with UI extensions in place** — extensions are a Shopify-CLI/Dev-Dashboard-app concept, and the admin-created-custom-app path is now closed to *new* app creation entirely. To add a UI extension or an embedded page, the team would need to **create a separate, new app via Shopify CLI or the Dev Dashboard**, scoped and installed independently, and grant it its own access (its own install step and its own token/session flow) — it would not "become" or share identity with the existing custom app. Rough migration effort: scaffold the new app (`shopify app init`), configure the same read/write scopes it needs, run `shopify app dev` to install a dev version on the same store (a store can have multiple apps installed side by side, so the existing token/app keeps working unmodified), then build the extension or embedded page inside that new app. This is additive, not migratory — nothing about the existing custom app's token needs to change.

### Recommendation
Keep using the existing custom-app token exactly as-is for all direct Admin API calls (metafield reads/writes, discounts). Only spin up a second, CLI/Dev-Dashboard-managed app if the team commits to §2 or §3 — budget that as a **new, from-scratch app setup**, not an upgrade path, and expect roughly the same first-timer time estimates given in §2/§3 above just for getting *an app of that kind* running, before extension-specific work starts.

### 5. Change notification for a metafield update

- **No dedicated metafield webhook topic was found.** The comprehensive webhook topics reference does not list a topic such as `metafields/update`. [Webhooks reference](https://shopify.dev/docs/api/webhooks/latest)
- **`products/update` and metafields:** the same reference does not explicitly state that the `products/update` topic payload changes, or that the topic fires, purely because a metafield value changed (separately from any other product field). This specific behavior is **UNVERIFIED** against the primary webhooks reference — it wasn't stated either way on the fetched page. (Community threads discuss a `metafieldNamespaces` filter parameter on webhook subscriptions that scopes *which* metafield namespaces are included in a `products/update` payload when it does fire, but that's about payload *content*, not proof that a bare metafield edit *triggers* the topic — and community threads are not a primary source, so treat this nuance as background only.)

### Recommendation
Given the topic's firing behavior on a metafield-only change is unconfirmed either way from primary docs, **don't build a webhook-dependent flow for this on a 32h clock.** The team's existing 60-second polling sync (re-reading the metafield via Admin GraphQL) is simpler, already built, and doesn't depend on an unverified webhook-firing edge case. **Judgement: keep polling; revisit webhooks only if there's spare time and a live re-check of `products/update`'s actual behavior on a metafield-only edit in the dev store.**

### 6. Native Shopify features that might already express a "floor"

- **Cost-per-item field & margin display:** admin has a per-product **Cost per item** field (Products → product → Price section) that, alongside the Price field, has Shopify "instantly calculate... Profit and Margin percentage." [Product pricing details](https://help.shopify.com/en/manual/products/details/product-pricing) mentions cost-per-item and margin tracking as an admin capability, though the fetched page's exact wording on the auto-calculated margin display was thin — **not applicable to this use case**: it's a display/reporting field, not an enforceable floor a negotiation engine can check against as a hard limit at request time (no API guardrail semantics), so it's informational, not a mechanism.
- **Compare-at price:** shown as a crossed-out "was" price next to a sale price on storefront/collection pages; not shown at checkout. **Not applicable** — it's a marketing-display field for showing a discount, not a floor/guardrail of any kind.
- **Price lists / B2B catalogs with quantity minimums:** Shopify's B2B catalogs support quantity rules (minimum/maximum order quantity per variant) and volume pricing tied to a company/customer group. [Quantity rules and volume pricing in B2B](https://help.shopify.com/en/manual/b2b/catalogs/quantity-pricing) — **not applicable**: this constrains *order quantity*, not a *minimum acceptable unit price* a negotiating agent could check, and it's scoped to B2B company accounts, not a general consumer-facing negotiation.
- **Shopify Functions — cart/checkout validation:** validation functions "run on Shopify's servers and can block checkout progress when business rules aren't met," and are available "for online store carts, carts built for custom storefronts, and throughout the checkout process." [About cart and checkout validation](https://shopify.dev/docs/apps/build/checkout/cart-checkout-validation) — this is genuinely **checkout-time-scoped**: it can act as a last-line hard floor at the moment of purchase (e.g., block checkout if a discounted line-item price fell below a threshold), but it is **not a fit for the app-side negotiation guardrail itself** — the negotiation happens earlier, inside the chat/agent flow, before checkout, and Functions can't see or influence that conversational step. It could be layered on *later* as a belt-and-suspenders backstop, but building the primary floor-price guardrail as a Function would be solving the wrong part of the flow.

### Recommendation
None of Shopify's native pricing features substitute for the "AI negotiation floor" the team needs — all are either display-only (cost/margin, compare-at), quantity-scoped (B2B catalogs), or checkout-time-only (Functions). The floor belongs in the team's own negotiation logic, reading a value from wherever §1's decision puts it (metafield or Console/DB); Shopify Functions is at best a stretch-goal checkout backstop, not the primary mechanism.
